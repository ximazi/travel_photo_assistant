旅行人物摄影助手：场景理解与拍摄指导原型
版本：v0.1
日期：2026-11-20


一、材料状态与用途

本目录是一套用于实现和评估产品原型的设计材料，包含提示词、结构化输出约束、拍摄知识卡、假设输入与输出，以及评价案例。

它不是已经部署的应用，也不是经过实拍验证的摄影系统。目录中的样例使用假设场景，没有附带对应的真实图片；样例数值、人物位置和场景观察不能作为真实视觉识别结果使用。本版本不对识别准确率、响应时间、成片提升幅度或设备兼容率作未经验证的承诺。

目标是把“看见当前画面”转化为“下一步怎样拍”，并让每条建议能够被执行、复查和评价。


二、v0.1 的范围

本版本以手机后置摄像头、单人旅行照为主要范围，覆盖海边、山林、城市街道等环境。默认目标是自然的环境人像：人物表现清楚，同时保留值得记录的旅行环境。具体景别、横竖构图和风格仍应由输入偏好与现场条件决定。

主要输出包括：

1. 当前画面中可以观察到的人物、环境结构、光线线索和构图冲突。
2. 一套推荐拍摄方案及其适用理由。
3. 人物目标位置、构图目标和需要保留的背景。
4. 摄影师与被拍者分别需要做的动作。
5. 与当前设备能力匹配的镜头或取景建议。
6. 当前最优先执行的一条指令，以及判断是否完成的条件。

本版本不把单帧图像当作真实三维测量结果，也不假定系统能看到画面外的环境。多人合照、前置自拍、复杂视频运镜等可以在后续版本中单独扩展。


三、建议架构：观察与规划分开

推荐流程如下：

输入预览图、设备能力和拍摄偏好
  → 场景观察
  → 根据观察结果筛选拍摄知识卡
  → 生成候选方案并选择当前方案
  → 服务端校验与必要的降级
  → 在预览画面中显示构图目标和当前指令
  → 端侧对齐检查
  → 必要时重新观察与规划
  → 拍摄与结果评价。

“场景观察”和“拍摄规划”是两个职责，不要求部署两个不同的大模型。可以让同一个支持图像输入的模型分两次调用，也可以在实验阶段比较单次调用与分阶段调用的效果。分阶段的主要价值是让观察事实、知识来源和拍摄建议可以分别检查。

观察阶段回答“画面里有什么，哪些关系能够确认”。规划阶段回答“在这些条件下，哪种照片值得拍，下一步如何完成”。观察阶段不能为了配合某张知识卡而虚构海岸线、可站立区域或光线方向。

推荐采用“慢语义规划＋快端侧对齐”的运行方式。大模型负责场景理解、方案选择和较大的方案修订；端侧检测、跟踪或姿态能力负责持续检查人物框、目标位置、画面倾斜等可测量变化。是否具备这些端侧能力，需要在具体平台上实现和验证。

系统应保留当前方案和当前指令，避免每张预览帧重新选择构图，导致用户不断收到相反操作。只有场景明显变化、目标人物丢失、执行条件不再满足，或者用户主动换方案时，才重新规划；具体触发阈值应通过实际测试确定。


四、纯提示词、固定知识卡和检索式知识库如何选择

方案 A：纯提示词。
适合建立最小基线，验证模型是否能理解画面并输出明确指令。实现简单，但摄影知识分散在模型与提示词中，容易出现宽泛建议，规则更新和失败归因也较困难。

方案 B：明确提示词＋固定少量拍摄卡。
适合本原型阶段。将少量经过整理的拍摄卡随请求提供，或者通过简单条件筛选后提供。可以明确检查模型选择了什么卡、适用条件是否满足、输出是否符合卡片约束。卡片数量较少时不必先建设向量数据库。

方案 C：明确提示词＋可检索的自定义知识库。
适合拍摄卡、风格、设备和场景覆盖逐渐增加以后。知识库保存可执行的拍摄方法，而不只是摄影散文。检索结果为模型提供候选知识，最终仍需结合当前画面和设备条件决定是否使用。

建议先按元数据条件检索，包括场景、人物数量、景别、光线线索、构图结构、可用镜头、动作前提等，再考虑增加语义或向量检索。向量相似度不能代替适用条件检查。例如，“海边电影感”语义相近，不代表逆光、站位和空间条件都满足。

知识卡应包含适用条件、构图目的、具体动作、设备条件、不适用情况及完成判断。检索不到适用卡片时，应回退到保守的基础构图建议，或明确指出缺少哪项信息，不能把相似但不适用的卡片强行套用。


五、场景识别重点与单帧证据限制

“海边、森林、街道”是场景标签；真正决定建议的是画面中的可用结构。

需要关注的人物与环境关系包括：人物占比和位置、重要地标、地平线、道路或岸线的延伸方向、前景与留白、背景杂物、肢体裁切、杆件与头部重合，以及脸部相对背景的明暗。

观察应区分明确可见、基于画面的推断和未知。置信度应反映对具体判断的把握，不能只给整个场景一个笼统分数。

单帧图像通常不能可靠提供人物的米制距离、摄影师应移动的精确距离、真实物理焦距、画外可站立空间或移动后的完整画面。因此，缺少设备或深度信息时，应使用相对取景目标与逐步反馈，而不是虚构“退后两米”“换成某个设备实际不存在的镜头”等指令。

镜头建议需要先确定景别、人物占比和背景保留目标，再映射到设备实际提供的镜头与变焦能力。手机上的变焦倍率不是跨设备统一的物理焦距描述；是否允许裁切、可用变焦范围及当前镜头信息，应由运行时提供。缺少这些信息时，保留当前镜头并给出构图目标是一种可用的降级方式。

光线判断也应基于证据。“脸部比背景暗”与“太阳必定位于人物某一侧”不是同一层次的结论。方向没有足够证据时，应保留未知，并通过新画面验证调整结果。

特别注意：仅转动手机改变朝向，或裁切画面，并不能消除背景杆与人物之间原有的遮挡关系。要改变这种关系，需要摄影师或人物发生实体位置变化，例如摄影师横向平移；前提是已确认具备移动条件，并且需要重新取景验证。不能从单帧直接推导保证有效的移动方向和固定米数。


六、坐标与预览显示约定

本原型的视觉坐标基于“已经完成方向旋转、没有镜像”的分析图像：

1. 按设备方向或图像方向信息先完成旋转，使图像处于正确朝向。
2. 分析坐标不施加水平镜像。
3. 左上角为原点，x 向右增加，y 向下增加。
4. x、y 均归一化到 0—1，分别对应分析图像的宽和高。
5. 具体点、区域和边界框的字段形式，以对应 JSON Schema 为准。

模型输出、检测结果、目标轮廓和完成检查必须使用一致的坐标系。终端展示时，应用需要把分析坐标映射到实际预览控件，处理旋转、缩放、留黑边、预览裁切和可能存在的显示镜像。

不要把归一化坐标直接乘以整个屏幕宽高，也不要把显示镜像重复施加到分析坐标上。用户可见的“左、右”应与最终屏幕显示一致；如果涉及被拍者身体的左手、右脚，应单独明确表达。

目标位置是构图意图，不是模型已经精确理解三维空间的证明。大模型估计的区域坐标应通过检测结果、合理性校验或实际对齐反馈复查。


七、目录内容

prompts/observer.system.txt
  场景观察阶段的系统提示词。约束观察范围、证据使用、未知项处理和结构化输出。

prompts/planner.system.txt
  拍摄规划阶段的系统提示词。结合观察结果、拍摄卡、设备能力和偏好生成可执行方案。

schemas/scene_observation.schema.json
  场景观察输出的结构约束，用于检查字段、类型、枚举和允许的数值范围。

schemas/shot_plan.schema.json
  拍摄方案输出的结构约束，用于检查方案、动作与相关输出的格式。

knowledge/shot_cards.json
  拍摄知识卡示例。可先固定注入或按元数据筛选，再逐步扩展为可检索知识库。

examples/runtime_input.json
  运行时输入示例，说明如何组织设备、拍摄偏好和必要上下文。示例不含真实取景图片。

examples/scene_observation.json
  假设场景的观察输出示例，帮助理解观察 Schema 和提示词的预期结果。

examples/shot_plan.json
  与假设输入相关的拍摄方案示例，用于理解目标构图、动作指令和完成判断。

evaluation/evaluation_cases.json
  评价案例与测试关注点，用于检查识别、条件适用、可执行性和反馈行为。

evaluation/evaluation_protocol.txt
  提示词与知识库的对照实验设计、现场拍摄盲评方法及结果记录要求。

integration_notes.txt
  应用层与供应商Schema适配、生产与虚构夹具隔离、引用及设备校验、人工动作边界等集成要求。

sources.txt
  能力边界与底层接口的官方参考资料。

README.txt
  原型说明、能力边界、坐标约定、接入步骤与评价方法。


八、接入步骤

第一步：准备实际输入。
从相机预览中取得图像，完成方向规范化，并同时收集当前镜头、可用镜头、变焦范围、横竖构图及用户偏好。不能用假设样例替代真实图像进行产品效果验证。

第二步：调用观察阶段。
将图像、相关运行时信息与观察提示词提交给支持图像输入的模型，要求按观察 Schema 输出。保留关联的帧标识，避免把旧画面的观察结果用于新画面。

第三步：校验观察结果并筛选知识卡。
先做结构检查，再检查关键字段是否有画面或设备证据。按场景结构和执行条件筛选拍摄卡。卡片缺失或关键条件未知时，应标明限制，而不是假设条件已经满足。

第四步：调用规划阶段。
提供观察结果、相关知识卡、设备能力、用户偏好和当前执行状态。可以使用同一个模型。规划输出需要明确当前方案和最优先的一步，避免在界面上同时显示多套相互矛盾的指令。

第五步：执行服务端业务校验。
校验知识卡引用、设备能力、动作前提、坐标关系、未知信息使用和完成条件。无效结果应修复、重新生成或降级；不能仅因为 JSON 解析成功就直接进入用户指令。

第六步：映射到界面并建立反馈。
将目标人物区域、地平线等映射到真实预览控件。每次先显示一条主要指令；通过端侧检测或新一帧观察确认执行结果，再进入下一条。

第七步：拍摄并记录结果。
保存用户选择的方案、实际执行的步骤、必要的观察与最终评价，用于定位失败原因。记录和保存方式应遵循产品自身的数据设置。


九、JSON Schema 之外必须实现的业务校验

JSON Schema 只能保证输出符合约定的结构，不能保证视觉判断真实，也不能证明建议能够执行。

服务端至少需要根据产品实际字段检查：

1. 知识卡标识存在，且卡片适用条件与已确认的场景条件相符。
2. 选定镜头、变焦及设置属于当前设备真实支持的能力。
3. 坐标合法且边界关系正确，目标区域没有明显超出画面。
4. 计划没有把未知距离、未知光向或画外空间当成已知事实。
5. 需要实体移动的指令具备足够的执行条件；条件不足时使用可验证的替代方案。
6. 当前指令与保留背景、目标人物位置和下一步指令之间不存在明显冲突。
7. 完成条件具有实际可用的观测方式。尚未实现对应检测能力时，不能自动宣告已经达成。
8. 方案、观察与当前画面和选定人物一致；失去对应关系时重新观察。

模型自报的置信度和“已完成”描述不能替代这些检查。摄影审美还需要真实照片与人的评价，不能仅通过格式验证推定。


十、评价与迭代

建议用同一组真实场景比较纯提示词、固定知识卡和检索式知识库方案。保持设备、输入偏好与评价口径一致，避免把不同拍摄条件造成的差异归因于提示词变化。

评价应覆盖四个层次：

观察质量：人物、地平线、重要背景与遮挡是否识别正确；无法确认的项目是否保留未知。

建议质量：指令是否明确、与当前画面有关、符合设备能力、满足动作前提，并且有合理的完成判断。

闭环质量：执行后的目标是否改善，是否出现反复变更方向、使用过期观察或长时间无法完成的问题。

成片质量：相同场景下进行前后照片或不同方案的盲评，关注人物表现、环境辨识度、构图和用户偏好，并记录执行成本。

应专门测试“同样是海边，但逆光、游客数量、人物位置和海岸结构不同”的情况。如果始终输出同一套三分法、侧身和焦距建议，说明系统没有充分使用当前画面的证据。

迭代时分别归因于观察错误、卡片不适用、方案选择错误、指令表达问题、设备映射错误或反馈判断错误。每次修改后使用保留案例复查，避免只让某一个示例看起来更好。

本版本的验收重点是建立可检查的完整闭环。具体质量门槛、响应时间目标、模型选择和最终上线条件，应在真实设备与实拍评价后确定。
